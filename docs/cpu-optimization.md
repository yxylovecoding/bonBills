# CPU 优化验证

核对日期：2026-11-04；基线提交 `f7c03bf`。本次只减少重复计算，不改变同步频率、排程规则、密码哈希参数或数据新鲜度。

## 修改

- 日期和时区转换复用 `Intl.DateTimeFormat`。进程内最多保留 32 个格式配置；不缓存账号数据、日程或日期对应的 UTC 偏移，夏令时仍按每个具体日期计算。
- 空档计算中的同一天时刻边界只转换一次，不再对每条日程反复计算午夜和日末；日历过滤范围也只计算一次。
- 一次 Outlook 读取中的全天场景与忙闲窗口共享 ICS 解析结果，分别展开重复日程。下次读取仍重新获取并解析订阅内容，不跨请求复用私人日历。

## 本地测量

执行 `npm run benchmark:cpu`。脚本只使用固定合成数据，拦截网络请求，不读取凭据或触发真实任务。每组预热一次，再取五次 `process.cpuUsage()` 的中位数；输出完整结果的 SHA-256 用于检查优化前后一致性。

环境：本机 Node v25.9.0。Render 运行 Node 24，以下是局部计算基准，不代表线上整站 CPU 或账单减少同样比例。

| 场景 | 优化前 CPU | 优化后 CPU | 减少 |
| --- | ---: | ---: | ---: |
| 5,000 次待办日期转换 | 128.95 ms | 12.52 ms | 90% |
| 160 个待办、2,400 条完成记录的每日排程 | 232.99 ms | 29.97 ms | 87% |
| 660 条日历事件、两个读取窗口 | 152.79 ms | 68.27 ms | 55% |
| 320 条日程、7 天空档计算 | 116.27 ms | 3.40 ms | 97% |

四组输出哈希均与基线一致。回归覆盖上海历史夏令时、洛杉矶夏令时切换、非整小时时区、无效时区、浮动日期、日历重复与改期例外、读取后内容更新，以及已有待办/空档规则。

Vercel 的按函数历史 Active CPU 查询要求 Observability Plus，未开通付费附加项；因此无法据此给出线上整站节省比例。Render 刚迁入，实际 CPU 与任务耗时需以之后正常业务负载为准。

## Render 健康检查超时修复

2026-11-04 16:11、16:41、16:50（北京时间），Render 记录 `server_failed`，原因均为 HTTP 健康检查超过 5 秒；部署构建正常，内存峰值约 157 MiB，低于 512 MiB。16:50 这一轮最后的阶段日志是 `exercise` 开始，之后没有结束记录便重启。排程期间的同步计算会阻塞同一 Node 线程上的 `/healthz`。

以只读取得的 331 个任务、1,620 条历史、3,347 天日历进行本地 CPU 采样，热点是按任务反复扫描整个场景日历并校验日期。原合成基准的日历为空，没有覆盖这个负载。合入 `346ebaf` 的训练修复：候选日期是否可用只查询当天，不扫描整个日历。普通每日排程则每轮建立一次场景日期索引，以二分查询下一日期；单独日期查找也只校验可能的最小候选。索引不跨排程或账号保留，查询仍尊重当前规则优先级。同时在同步规则之间让出事件循环，使健康检查和其他 HTTP 请求有机会响应。

同一真实快照预热后取三次中位数：CPU 从 1,017.712 ms 降到 68.712 ms（约 93%），墙钟时间从 1,006.108 ms 降到 50.150 ms。完整结果 SHA-256 均为 `377bac3afc141b9eb51c4f50dd6c0104e24e0329436b2673f9b3dac2b530c07b`，没有触发生产写入。此比例只代表本地纯排程计算，不代表整个同步请求或线上耗时。

`npm run benchmark:cpu` 增加了带场景标签及 3,347 天日历的固定合成用例。回归覆盖无效日期、乱序日历、多个场景、无未来场景、日历更新、规则顺序改变，以及阶段之间处理事件循环回调。
