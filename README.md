# monthlyBills

个人财务管理 Web 应用（盘账助手）— 由 `PLAN.md` 驱动开发。

## 当前状态：MVP 测试版

本阶段只做视觉骨架，用于评审页面布局和风格。数据全部来自 `src/data/mockData.ts`（从 `PLAN.md` §初始数据 摘取），不落盘、不做真实计算。

## 本地运行

```bash
npm install
npm run dev       # 开发模式 (http://localhost:5173)
npm run build     # 生产构建
```

## 安装为应用

应用使用各自的独立域名：

| 应用 | 独立入口 |
| --- | --- |
| BonBills | https://bill.bonbills.cn/ |
| BonLog（原 BonLife） | https://log.bonbills.cn/ |
| BonCV | https://cv.bonbills.cn/ |
| BonClothes | https://clothes.bonbills.cn/ |

BonBills、BonLog 和 BonClothes 均提供独立名称、图标和安装入口，登录前也可安装。用浏览器打开对应域名，再选择「独立安装」；iPhone/iPad 使用 Safari「分享 → 添加到主屏幕」，桌面 Chrome/Edge 使用安装菜单。从已有应用内部打开时，可复制独立入口到浏览器后安装，各应用从自己域名的根路径启动。BonCV 继续由独立的 BonCV 项目提供服务。

原 `bonbills.cn`、`www.bonbills.cn`、`/life`、`/clothes` 继续可用，新增 `/log` 入口。旧 `/life` 清单保留应用 ID 和启动路径，仅更新显示名称为 BonLog。域名独立保存登录会话，BonBills、BonLog 和 BonClothes 使用原账号密码及原服务端数据；本地草稿和未同步修改仍留在原域名。应用身份在 `src/utils/apps.ts` 统一定义，图标与清单位于 `public/`。不提供离线页面缓存。

## BonClothes 衣柜与今日穿搭

`clothes.bonbills.cn` 根路径及主站 `/clothes` 独立加载 BonClothes，不启动财务同步。主站复用已有登录会话，独立域名使用原账号密码且会话单独保存，衣柜数据共用。提供「今日」「衣柜」两个页签，以及独立标题、图标、安装入口；独立域名使用 `/bonclothes-root.webmanifest`，主站使用 `/bonclothes.webmanifest`；支持手机和桌面，不提供离线页面缓存。

衣柜通过照片和手动标签录入，支持编辑、分类、状态筛选、删除与可穿／待洗／收起切换。分类为文胸、内衣（秋衣、保暖衣等贴身内搭）、上衣、下装、连衣裙、外套、鞋、配饰；旧「上装」兼容显示为「上衣」，无须迁移。上衣及连衣裙可设置「需穿文胸／可不穿文胸」，未设置时默认需穿文胸；内衣不设置也不参与文胸判断。照片在浏览器压缩至最长边不超过 960px、单张不超过 200KB；普通照片使用 JPEG，带透明区域的图片使用 WebP（浏览器不支持编码时回退 PNG），不填充白底。仅保存展示图片，原图不上传；白底原图不会自动抠图。服务端检查 JPEG／PNG／WebP 的实际文件头、容器边界和尺寸，鉴权读取时返回匹配的图片类型。既有 JPEG 和历史图片继续可用。

「今日」按设备当地日期、IANA 时区读取现有 Outlook「玩／课」订阅的全天与定时日程，可选读取 LOCATION；既有账本仍沿用上海时区。明确活动预填场景及「运动／多走路」；健身、球类、徒步或大量步行要求衣物方便活动，普通公园、露营等室外场景不自动等同于运动，未知活动保留「待选择」。手动修改逐日保存，日历刷新不会覆盖。日程地点需经城市搜索选择，可区分同名城市；不会自动覆盖当前地点。进入今日时自动请求定位，首次由浏览器询问授权；已授权时自动刷新，手选优先，拒绝或失败时回退到上次手选城市，也可点击定位切回当前位置。天气通过服务端读取 [Open-Meteo](https://open-meteo.com/en/docs) 的气温、体感、降水和风速，按地点、日期与时区缓存 30 分钟，失败保留旧天气并标注时间，也可手填温度和雨况。

规则只组合可穿衣物，支持上衣＋下装＋鞋或连衣裙＋鞋，按低温、温差、雨和风增加外套与配饰。上身、下身分别按 26℃ 目标匹配；头、脸、脖子、脚、手使用各自的保暖档位，袜子与鞋独立选择，薄／常规／厚袜的初始值为 0.5／1／2。保暖帽低于 10℃ 才参与匹配，厚帽仅在室外低于 5℃ 时推荐；围巾、口罩、手套分别按自己的低温阈值选择，不按 26℃ 补齐。名称可识别帽子、口罩、围巾、袜子、手套，也可在配饰编辑中指定保暖部位；不同部位的配饰可同时推荐、替换及保存，最多 24 件。全身体感记录只校准上身、下身衣物，不推算鞋袜和配饰的保暖值。低温时可搭配保暖内衣；根据上衣或连衣裙的设置添加文胸，文胸不足则显示缺少类别，炎热时不额外添加保暖内衣。防风外壳结合内层保暖程度判断，厚内胆与薄外壳可一起推荐；零下仍要求外套本身保暖。单件替换会重新校验整套叠穿条件并同步调整文胸。先满足天气、室外与行动需求，再比较颜色和近七天穿着次数；相同输入结果稳定，可换一套或单件替换。衣物不足时显示现有衣物和缺少类别。「今天穿这套」逐日保存实际搭配，再次确认替换当天记录，不自动标为待洗；确认后天气刷新不改变搭配。历史在今日页内展开，保存衣物名称、标签、不可变图片引用和当天条件快照，删除或修改衣物后仍可阅读。

「出行穿搭计划」在今日内展开，读取已有出游分段、名称和 Outlook 日程，保留设备当地日期；选择具体目的地后按目的地时区展示逐日预报。Open-Meteo 最长提供未来 16 天预报，超出范围显示「待预报」。逐日调整场景、运动或多走路、选搭及单件替换，点击「保存计划」后刷新可恢复；计划存入 `bonclothes:trip-plans:v1`，不会生成实际穿搭记录或修改出游、日历。目的地变化清除旧选搭，行程变更保留已存计划供核对。预报独立缓存 30 分钟，失败可重试并显示旧预报时间。

`/api/bonclothes` 受现有登录、同源校验保护，生产重写到 `/api/outlook-calendar?app=bonclothes` 并分派到 `_bonClothesRoute.ts`，本地 Vite 使用同一处理器，不增加部署函数数。衣物、每日条件、出行计划、历史和照片使用独立的 `bonclothes:*` KV 键；Lua 原子事务校验逐项版本、照片和确认时衣物状态，30 天请求回执保障重试幂等。冲突保留浏览器编辑，用户可核对后沿用当前内容再次保存；断网可重试，草稿按账号保存在当前浏览器。无需迁移数据或新增密钥，不写 Outlook、TickTick 或财务账本。

验证：`npm test` 执行推荐规则、接口、天气、时区和已有功能回归；`npm run build` 执行类型检查及生产构建。浏览器验收可按「新增照片 → 调整当天条件 → 换装／单件替换 → 确认 → 刷新 → 历史」检查，并核对 `/clothes` 直接访问、未登录照片保护和手机布局。

## BonLog 状态日历

`log.bonbills.cn` 使用同一 Vercel 项目提供独立的 BonLog 首页、图标和皮肤／情绪／运动等追踪；主站的 `/log` 与原 `/life` 均可访问。域名绑定到原 Vercel 项目，在 Cloudflare 配置对应 CNAME。内部 `/api/bonlife`、`bonlife:*` 数据键和旧图标文件名保持兼容，无需迁移数据。沿用已有账号密码，子域名登录状态单独保存，不加载账本及其同步任务。

点击日期格编辑皮肤、眼睛、身体、情绪或训练。「眼睛」统一记录症状，不再区分左右眼；「身体」保留左骶髂、右骶髂和腰。症状首次填写后可直接点选复用，每天分别记录出现、持续、好转、加重或消失及备注。「症状跟踪」按症状显示记录次数、首次日期和历史状态，可点击历史日期继续编辑。旧的左右眼文字保留为症状及部位备注，旧记录不推断变化状态。新保存的症状同时写入独立的 `bonlife:symptom-entries:v1` 索引，跨年复用及跟踪；读取时也纳入所选年及上一年的旧记录。移除当天症状后保存只清空当日记录。「训练 → 身体数据」提供趋势图和记录列表，不显示月历；选择记录日期后新增数据，点击历史记录修改，可按年或月查看。皮肤分别记录早间、晚间用药和护肤品；体围记录胸、腰、臀、上臂、大腿、小腿围，单位 cm，支持小数和单项留空。年月选择及「往年同月」可查看、补记往年。记录按年存入独立的 `bonlife:entries:v1:*` Redis hash，每次只更新一个类型的一天，使用版本检查避免覆盖其他页面的修改。清空后保存即清除对应内容；版本标记保留，防止旧页面恢复已清空的内容。编辑中的完整草稿按账号暂存在浏览器，刷新后可继续；成功保存或明确放弃后移除。已有纯文字记录保持兼容。

「经期设置」默认自动更新：合并手动开始日期与 Outlook 已记录的连续经期，取最近 6 个有效开始日间隔的中位数估算周期（沿用 21–45 天的输入范围），取最近 6 段已结束、长度 2–10 天的连续记录中位数估算经期。单日标记只作为开始日；未来、正在进行的区间不用于学习经期长度。无有效样本时使用可编辑的初始值；可关闭自动更新手动设置。最近开始日期与下次预计日期随记录更新，过期预测显示待确认，不写回实际记录。保存设置不把仅展示的 Outlook 日期复制成手动记录。跨年和浏览远期月份仍读取当前年份附近的历史。

训练安排沿用四段模板，月经期长度改为记录估算或手动设置的天数；后续阶段按周期比例划分，28 天模板后两段从第 14、20 天开始。实际记录的经期优先。图示阶段是训练分组，不能用于判断实际激素水平、排卵或避孕；日期推算标为「预计」。训练页提供各阶段运动、饮食建议以及每日计划，经期前 3 天默认安排轻量活动，之后渐进恢复，黄体早期侧重力量，中晚期适当减量。可以选择轻量、休息或自行编辑并标记完成。已保存计划不随设置变化而覆盖；未保存日期随当前设置更新。没有经期日期时不推算。

运动建议是可调整的安排，不假设所有人的运动能力随周期固定变化。参考图的阶段与饮食方向经过改写：保留富铁食物、足量蛋白质、按训练量补充碳水、鱼类坚果与全谷物；不把「燃脂黄金期」「冲大重量」或「特定阶段运动会导致黄体破裂」写成普遍结论。图中所引 [McNulty 等的系统综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC7497427/) 指出效应很小、研究差异较大，应采用个体化安排。其他内容参考 [美国卫生与公众服务部女性健康办公室](https://womenshealth.gov/getting-active/physical-activity-menstrual-cycle) 和 [ACOG 经前综合征建议](https://www.acog.org/womens-health/faqs/Premenstrual-Syndrome)，不提供用药或补充剂处方。

「DoneList」复用 BonBills 已连接的 TickTick，按上海时区的实际完成日期汇总所有清单及收集箱中的任务。打开页面自动同步所选月份，可切换往月、往年补拉可用历史；页面可见时每五分钟刷新。每日现有后台任务也保存当前月份完成记录，月初补存上月末。记录存入独立的 `bonlife:done:v1:YYYY-MM` hash，以清单、任务 ID 和完成时刻区分重复任务的每次完成。重复读取不会重复计入，源端不再返回的旧记录、断开连接或同步失败均不清空已保存历史。首次补拉受 TickTick 实际提供的历史范围限制；仅归档任务，不修改 TickTick 完成状态或排期。密集结果分段读取，读取失败不标记同步成功。

在 BonLog 右上角 Outlook 入口填写 Outlook「日历」的 ICS 订阅链接。此连接与 BonBills 的「玩／课」连接独立，链接加密保存在服务端；未连接时仍可写日历。同步仅读取标题包含「月经／经期／例假／大姨妈／🩸」、且不含「预计／预测／预估」的全天日程，按事件的完整日期范围在两份状态日历显示经期，结束日期遵循 ICS 的不包含规则，支持重复、排除、改期和取消。进入某一年时自动同步该年，也可点击「同步经期」。

经期还会通过 `.github/workflows/ticktick-daily-plan.yml` 的独立归档任务，按北京时间每天 05:00、12:00、17:00、20:00 自动导入并持久保存；GitHub 定时任务可能延迟执行。任务复用现有 `BONBILLS_CRON_SECRET`，调用受保护的 `/api/ticktick-trips?action=life-periods`，无需打开网页或连接 TickTick，也不受任务写锁、训练安排及其他日历失败影响。每次只拉取一次经期订阅，更新上一年、当年、下一年的快照以覆盖跨年记录；未连接时跳过，失败重试并保留已有历史。网页页脚显示保存时间，导入的新记录继续用于自动估算。工作流支持 `periods_only` 手动补同步；经期导入结束后才继续原有排期，导入失败也不跳过原排期。

经期快照按年保留。仍在订阅中的事件以最新内容为准，包括更名、改期和取消；已从订阅范围消失的历史日程保留过去部分，未来部分不沿用。同步失败时保留上次完整快照，断开连接也保留历史标记。首次导入只能取得 Outlook 当前发布范围内的历史事件；尚未被订阅提供过的往年经期无法凭空补齐。

本地 `/life` 复用与生产一致的 `/api/bonlife`；需要现有 `SYNC_SECRET` 和 Vercel KV 环境变量。生产将此地址重写到 `/api/outlook-calendar?app=bonlife`，分派到独立处理器，以沿用现有部署函数数量；本地开发直接分派到同一处理器。BonLog 的经期与文字不进入财务账本的上传、合并或自动入账。

本地登录需要在 `.env.local` 配置 `SYNC_SECRET`、`KV_REST_API_URL`、`KV_REST_API_TOKEN`，建议连接开发用 KV。Vite 会转发登录及账单相关接口到同一份服务端实现。

## 登录

BonBills、BonClothes、BonLog 共用账号和注册入口。注册只需账号、密码（至少 6 位）和确认密码，不再显示或要求 Key；前端与服务端都验证两次密码一致。注册后自动登录，同名重复或并发注册不能覆盖已有账号。

不再使用固定的 `bon` 账号或把 Key 当默认密码，旧的 `LOGIN_USERNAME` / `LOGIN_PASSWORD` 环境变量不再生效。

原账号首次被读取时，将原绑定中的用户名、密码盐和密码哈希原样保留到固定的账号索引，原绑定也保留；不会重设密码、搬移或清空旧账本、衣柜、日志及连接。旧账号的用户名在开放注册前先被保留，不能被新用户抢占。以后账号密码与账号 ID 关联，登录不再依赖 Key。旧链接和旧 Cookie 继续兼容。部署时保留现有 `SYNC_SECRET`，它仍用于旧绑定的首次识别、后台脚本鉴权和外部连接加密。

新账号使用独立的账号 ID 保存账本、手动备份、衣柜照片、日志、Outlook/TickTick 连接和同步状态；原账号保持原有存储键。请求级存储隔离也覆盖 Lua 脚本和并发请求。现有定时任务继续操作原账号，环境变量配置的邮箱与 BonCV 私人代理仅原账号可访问。浏览器缓存与未上传修改也按账号独立保存，页面打开后固定归属；原账号继续使用原缓存，不搬移或清理。其他标签页切换账号后，延迟保存也不会覆盖新账号的数据。

浏览器登录状态保存 30 天，退出后服务端会话立即失效。密码以随机盐和 scrypt 哈希保存；原始密码和 Key 不写入账号记录、前端配置或浏览器持久存储。账号和会话存储于原有 Vercel KV，并保留登录、注册的尝试次数限制。

再次打开时，服务端验证登录后会先显示该账号上次完整同步的本地账单，再后台获取最新数据。首次使用、缓存缺失或损坏时仍等待完整同步；升级后的首次成功同步会建立缓存标记。同步失败时保留已显示的数据，并可在右上角重试。

登录和账单请求每次最多等待 30 秒；恢复登录状态和读取账单遇到超时或网络中断时自动重试一次，登录、注册和保存请求不自动重复提交。持续失败时显示中文状态并保留重试入口。旧 Key 链接只在登录成功或确认 Key 无效后清除，网络失败时可继续重试。

后台同步会保留等待期间的本地编辑，未修改的字段采用云端值；同一字段两边都有变化时保留本地编辑。尚未上传的修改保存在本地，刷新后继续尝试合并和保存。输入框编辑及导入预览结束前暂缓应用云端数据，自动入账与日历补填等操作等启动同步成功后运行。缓存仅用于浏览器显示，登录和账单接口继续禁用公共缓存。

## 163 邮箱账单导入

## 待确认基金买入

进入 Web 后会自动查询当前月份待确认基金的历史单位净值。对应净值公布后，自动把预估份额和买入成本计入持仓，并隐藏原待确认行，页面只展示更新后的持仓。按北京时间 15 点截单，周末及净值记录中暂停申购的日期顺延。净值未公布时继续等待，同一基金同月份复用查询，缓存 15 分钟；查询失败一分钟后重试，切回页面也会检查更新。

手续费明确时先扣费计算，未知时暂按费前份额入账；缺少操作时间、金额、明确基金报价源或订单身份有歧义时继续等待。下次导入正式账单时，后台匹配原自动入账记录并校正份额、净值、手续费和成本，重算后续买卖的影响；重复导入和旧待确认记录不会再次累加，校对标记仅内部保存。跨月迟发的净值入当前月份，保留此前月末快照；银行实际确认日期另存于交易记录。导入预览期间暂停自动入账。

## BonCV FIRE 联动

首页 FIRE 可以从 BonCV 单向同步出生日期、最高学历和毕业日期。BonCV 连接密钥只保存在服务端，浏览器通过受登录会话保护的代理读取最小字段。

```bash
BONCV_API_BASE_URL=https://你的-boncv-域名
BONCV_API_KEY=从 BonCV“连接”页面创建的 fire:read 密钥
```

连接失败时会保留上次成功快照；也可在 FIRE 详情中切换为手工维护。

FIRE 年薪从预计毕业就业时间起算，每满一个就业年度上涨 10%；在读期间沿用记录中的月均收入和在读支出，不生成工资或公积金。默认情景为杭州无房、非杭州户籍、当前公积金余额 0。

FIRE 后的居住场景可单击切换“寄 / 居”，“旅”为独立开关。独居使用“校”的日常支出样本，并加上“未来固定支出”中已启用的房租；在家不计这笔房租，其他固定支出照常计入。旅行按历史天数占比加权日常支出（包含记录中的旅行住宿），长期房租仍按全年计入一次，出游期间两种住宿开销同时承担。旧的“校 / 校＋旅行”配置分别沿用为“独居 / 独居＋旅行”。此开关仅改变退休后的支出，毕业前和工作期的支出保持原有分段。

公积金按个人与单位同额缴存。无房且设置租房支出时，青年或新市民按双边缴存额计算租赁提取，普通杭州市区租赁限额为 2000 元/月；同一期间在适用情形中取较高额度，不叠加，实际提取不超过账户余额。新就业连续缴存满 3 个月后计入首次提取。未提取余额单独累计，不预估利息；按 FIRE 时离职、不再就业缴存且封存满半年后的余额提取测算，折回目标时点，并保留半年生活费及大额愿望所需流动资金。当前公积金余额不能同时计入理财总额。户籍、落户日期、余额和提取开关可在现有 FIRE 详情中维护。

政策依据：[租赁提取政策](https://zfgb.hangzhou.gov.cn/11/105220253/t117220253054/518769.shtml)、[青年与新市民实施细则](https://gjj.hangzhou.gov.cn/art/2023/12/29/art_1229468386_1839436.html)、[离职提取新政](https://zfgb.hangzhou.gov.cn/11/105220253/t119220253054/519177.shtml)。

## Outlook 月历同步

「记录 → 月 → 设置」中的 Outlook 入口支持订阅「玩」「课」日历。在 Outlook 网页端的「设置 → 日历 → 共享日历 → 发布日历」中，分别生成可查看标题的 ICS 链接，在此处填写后预览本月，再点击「连接并同步」。订阅链接让持有者可以读取已发布范围的日历，请使用与自己期望一致的共享范围；应用将链接加密存于服务端，不写入浏览器持久存储、代码仓库或普通账本备份。Codex 的 Outlook 授权与网页连接独立。

全天「玩」映射为出游，其中标题「🏠」映射为寄，「新卡池」「新卡池&新月卡」忽略；全天「课」中标题恰为「实习」的日程映射为班，其他全天日程也映射为出行（包括出差）。非全天日程不参与场景标记，仅用于每日待办的忙闲计算；两个日历中标题恰为「寒假」「暑假」或「教师节」「中秋节」等已知节日名称的提醒均忽略，不按关键词包含关系排除「寒假旅行」或「平遥电影节」等具体出行。多日事件不包含结束日期；重复日程按发生日展开，支持 EXDATE、改期和取消单次日程。同日冲突依次优先游、寄、班。解析或任意一个日历读取失败时保留原有标记，不把不完整结果作为取消。

出游日期始终以 Outlook 为准：完整行程覆盖本地的班、学、寄及手动留空，避免周模板把连续旅行隔成数段；缩短、改期或取消时恢复此前接管日期的原有日常标记，不恢复旧出游日期。前台、后台及旧页面上传均沿用此规则。其他日常标记默认保留手动结果；首次接入时，旧版已有的非「学」标记也会保留，旧版「学」无法区分自动补填与手动设置，作为默认值处理。也可在连接时选择日常标记以 Outlook 为准。标记及来源信息沿用账本云同步，参与已有实习天数、出游和心愿计算。

生产环境每天北京时间 05:00、12:00、17:00、20:00 的后台任务先拉取 Outlook，再按最新云端日历执行 TickTick 排期，无需打开 BonBills；未连接 TickTick 时仍会拉取 Outlook。后台按上海日期读取过去 30 天至未来 700 天（结束日不含），沿用已保存的订阅、映射规则及手动优先设置，任一日历读取失败会保留原数据并停止本轮排期。此任务由 `.github/workflows/ticktick-daily-plan.yml` 的 GitHub Actions 定时调用 `/api/ticktick-trips`，支持手动触发，工作流串行执行；服务器忙时最多等待重试两次，其余失败直接报告。Vercel 中仅保留月度备份定时，避免重复排期及 Hobby 每个定时任务每天仅一次的限制。生产环境须配置 `CRON_SECRET`，同一密钥保存为仓库 Actions secret `BONBILLS_CRON_SECRET`；工作流不输出密钥、响应正文或私人任务信息。GitHub 按 UTC 调度，换算后的北京时间为上述四个时间点，高负载时可能延迟；公开仓库长期无活动也可能停用定时工作流。TickTick 明确返回每分钟查询限流时等待 30 秒后重试，最多两次；其他写入错误不自动重放。

普通「今日事」另外由 `.github/workflows/ticktick-hourly-plan.yml` 在每小时第 7 分钟自动重排，复用 `BONBILLS_CRON_SECRET` 调用 `/api/ticktick-trips?action=hourly-replan`。只读取最新日历与完成记录，按最久没做的优先更新普通任务日期；不执行完整同步、显隐、训练、洗衣或发信。凌晨 00:00–05:00、临时标签未恢复或未连接 TickTick 时跳过，与原工作流共用并发组和写锁。公开仓库的标准 GitHub Actions 定时触发免费，不调用 AI；服务器与存储仍计入现有平台额度。调度可能延迟。

TickTick「立即同步」同样先拉取上述完整日期范围的 Outlook 日程，再执行待办排期并清理失效的未来行程实例，因此无需逐月打开日历才能更新寒暑假等规则。清理沿用保存的生成任务 ID，不按名称删除普通待办；订阅读取失败时保留原任务。

进入或切换月份时仍读取当前月；页面可见时每五分钟刷新，回到页面时也会在超过五分钟后更新，并可点击「同步本月」。前台和后台都保存完整读取结果，旧页面上传时会按最新结果重新合并日历，保留明确的手动修改及账单字段。数据范围及更新延迟受 Outlook 发布的订阅内容影响，并非实时推送。对已过去的日期，订阅中缺失的日程不会自动清除已保存的标记与名称；有明确的新日程时仍更新，今天及未来的改期或取消继续正常同步。保留的历史同时写入服务端重放缓存，防止旧页面上传覆盖历史。断开连接会删除服务端订阅链接及同步快照缓存，保留已同步日历结果。

首页日历、月历及 TickTick 行程任务标题优先使用所选账单标签，没有标签时使用 Outlook 出游日程名称，两者都没有时用日期。日程名称不写入账单标签、筛选条件或消费归类；同步改名或取消时更新对应月份的备用标题，并触发 TickTick 任务名称更新。

「本月出游」中有名称的行程会自动创建并关联心愿，包括尚未选账单标签的 Outlook 行程及已结束的行程；没有名称的日期段待命名后补建。优先复用已经关联或唯一同名的未关联心愿（匹配时忽略账单标签的日期前缀和空格），保留预算、已攒金额、名称和启用状态。新心愿默认启用、金额待填写，截止日为出发前一天；跨月行程只建一项，手动切分后按各段关联。补建在账本完整加载及日历、出游编辑后执行，写入云同步，不需要先打开「心愿」。主动删除心愿或解除关联后，该出发日不再自动补建，仍可手动重新关联；行程取消时保留已有心愿及金额。

心愿中的「x 笔账单」在当前卡片内展开或收起匹配的账单明细，按日期从近到远展示日期、备注或分类、账户及金额；包含行前付款、跨月消费和退款，一笔账单命中多个匹配标签时只显示一次。查看明细不切换页面，也不提供手工录入入口。

已花总额和行程结束后的实际花销保留全部匹配支出，同时分别显示消费、生活及待分类金额。`消费` 标签计入心愿内欠款、已还和待攒金额；`周期生活`、`波动生活`（兼容 `生活`）只展示实际支出，不增加心愿攒款。未结束时从目标中扣除预估与实际生活费的较高者，不重复扣除；行程结束后只按实际消费计算资金需求。各类退款抵扣各自支出，生活退款不抵消费欠款。缺少核心标签或同时标为生活与消费的账单显示待分类，不直接当作消费；手填总欠款仍保留原值。首页、月度及实习阶段规划共用这一计算。

服务端沿用 `SYNC_SECRET` 和 Vercel KV，无需微软应用密钥。ICS 解析库只在服务端使用。部署后需首次填写订阅链接才会开始同步。

## TickTick 出游与场景待办

日历中的进行中及未来出游可以自动同步到 TickTick。首次使用时，在「记录 → 月 → 设置」中粘贴 TickTick 网页端“设置 → 账户 → API Token”生成的个人令牌。同步会在所有清单及收集箱中按名称查找 `出门todo模版`（兼容 `出门todo模板`）任务树作为动态模板，模板本身无需填写日期，也不要求存在 `出门当天`。一级子任务按名称（如 `出门前七个月`、`出门前两周`、`出门前3天`、`出门当天`）相对行程开始日排期，月和年按自然月计算并钳制月末，二级及更深层子任务始终跟随母任务的实际日期（包括母任务手动改期或清空日期）；生成的行程父任务统一使用“出行名称 · 出门todo”命名，只有原始模板保留“模版／模板”后缀；阶段及子任务继续使用“出行名称 · 原任务名”命名。已有行程父任务会在下次同步时原地更名，保留任务 ID、完成状态及手动日期。

出游候选标签仅会被当前仍存在的其他行程占用；已删除或重新切分行程留下的历史关联不会隐藏候选项。

已启用、设有截止日且未关联出游的心愿，以心愿截止日作为预计出发日，只同步 `出门todo模版` 中的 `出门前七个月`（兼容 `出门前7个月`）及其后代任务。阶段根任务定在截止日前七个自然月，月底不足对应日时取当月末；该阶段的所有后代任务日期与母任务一致，模板任务原有日期不参与任务排期。旧实例同步时按新规则更新自动日期，保留一级母任务的手动改期或清空日期。任务名称包含心愿名，按心愿 ID 更新改名和改期，保留完成状态；关联出游、停用或删除心愿后清理尚未到截止日的独立副本，日历完整出游任务不受影响。无截止日的心愿不生成，缺少唯一七个月模板时会报错。

出游的一级阶段任务、心愿准备的阶段根任务及 checklist 项保留手动改期或清空日期。二级及更深层模板子任务始终跟随母任务，单独修改子任务日期会在下次同步时恢复为母任务日期；一级母任务的手动日期不影响其他一级阶段。未手动调整的一级阶段按名称跟随行程或心愿截止日。模板原树、已生成的出游和心愿准备任务使用上述行程规则，不参与普通待办的场景标签排期。

API Token 使用 `SYNC_SECRET` 派生密钥加密后保存在服务端；修改行程或模板后会自动更新对应任务树，取消尚未结束的行程时会同步删除。

住宿分类使用「寄／居／旅」，日历保留「班／学／寄／游」四种标记：父母家为「寄」，「班／学」对应日常住所「居」，「游」对应旅行住宿「旅」。内部日历类型与历史数据保持兼容，班、学仍分别参与原有财务计算。

TickTick 中所有清单及收集箱内的未完成待办，按自身的「寄／居／旅」标签自动排期，兼容旧标签「寓→居」。「游」是普通分类标签，不触发旅行排期；需要旅行自动排期的待办使用「旅」。不再依赖 `在家routine／在校routine` 父任务或同名清单，不继承父任务标签；没有符合条件的待办时正常返回零项更新。

日期从上海日期的今天起查找，包含今天：「寄」取最近的寄日，没有时取今天或未来最近的春节；「居」取最近的班／学日；「旅」取最近出游开始日，正在出游则取今天。居／旅找不到日程时保留原日期。多标签比较所有有效候选日期并取最近的一天，每条待办仅更新一次。

带「居／寓」或「旅」的长周期重复任务（每隔多天、每周、每月、每年，以及限定部分日期的非每日规则），在当前场景匹配任一自身标签且已有日期时，保留滴答生成的下一次日期，逾期日期和 checklist 日期也不重排。离开所有适用场景后，统一移到日历中最近适用场景的首日，即使原定日期更晚；进入场景后由滴答继续按原重复规则循环。今天没有明确场景、找不到未来适用日或无法识别重复规则时保留原日期，不反推已被旧逻辑覆盖的历史日期。仅带「寄」的任务、普通「游」标签及每日任务沿用原规则。

需要改期时，已有日期的任务平移日期并保留时刻、时区及起止间隔；无日期任务补上目标日的全天起止日期。Checklist 仅调整已有日期的未完成项，无日期项不补期，已完成项保持原状。每日重复任务今天已完成时，从明天起重新比较全部标签候选日；连续出游中的明天也可作为旅日。长周期任务当天完成后生成的下一次日期，在适用场景内也保持不变。每次写入后回读验证，保留原重复规则及其他字段。

带「洗头」标签的未完成待办，统一跟随标题恰为「洗头」的唯一未完成待办的日期（有截止日期取截止日期，否则取开始日期，按来源任务时区判断）。日期跟随优先于寄／居／旅及自身循环排期；先完成出游、心愿和来源任务的正常排期，再同步所有清单及收集箱中的跟随项，包括本轮新生成的待办。保留各自时刻、时区、起止间隔和重复规则，Checklist 沿用上述改期规则，已完成记录不改动。来源完成后，下次同步跟随滴答生成的新待办日期；来源不存在或无有效日期时保留跟随项原日期，存在多个同名未完成来源时明确报错，不猜选来源。标题为「洗头」的任务本身不自我跟随。

每日动态安排复用每天北京时间 05:00、12:00、17:00、20:00 的后台同步及「立即同步」。沿用 bon 的智能清单范围：今日事为今天的中／低／无优先级任务，明日事为无日期、逾期及未来 30 天任务，均排除 `routine／不关我事` 标签。寄／居／旅限制先确定可执行日期，再在当天可做的任务中根据周期压力、最后实际完成时间挑选；今日未选中项移到明天或下一个适用场景日；明日事中只有入选任务移入今天，未入选项保留原日期（包括无日期）。高优先级任务保留原有排期，展示估时但不额外扣除普通待办额度。固定时刻、无法解析的循环、出行及心愿模板树、洗头日期跟随不参与普通轮换；普通子任务使用自身标签独立参与。

“香香喷雾”和“除螨喷雾”不能安排在同一天：冲突时保留较久未完成的一种，另一种移到下一个符合寄／居／旅标签且没有相反喷雾的日期。今日已完成的一种也占用该日期；未来日期、两种一起延后、高优先级和定时喷雾均检查，保留时刻和重复规则。没有可用的后续场景日则报告冲突，不写入违反规则的安排。只匹配这两个任务名称（可带时长标注），不匹配采购、说明、模板及不关我事任务；简报与用时统计按最终错开的日期生成。

每日用时默认跟随 Outlook 空档自动计算，不再使用固定 30 分钟额度或按重要事项数量打折。后台复用「玩／课」订阅的同一次读取，另展开过去 14 天至未来 31 天的具体时刻日程，保留时区、跨日、重复、排除、改期与取消；标为空闲的日程不占时间。全天标记继续用于寄／居／旅。任一订阅读取失败即停止本次排期，未连接 Outlook 且未设置手动上限时只保留原场景排期，不猜测空闲时间。

可用时段默认上海时间 09:00–11:00、14:00–18:00、20:00–22:00；11:00–14:00 为午饭与休息、18:00–20:00 为晚饭与休息，所有模式均排除这两个区间。全天实习／出游仍预留 09:00–18:00。每次执行都从实际重算时刻裁剪当天可用时段：12 点只算午后，17 点只算剩余下午和晚间，20 点只算剩余晚间；定时任务延迟时按实际执行时刻计算，摘要也只反映本轮剩余额度。扣除剩余具体日程及原定普通任务后，其余空档均可用于挑选待办，不再保留额外休息缓冲，也不为未定时的重要事项另留时间。也可选择仅晚间 20:00–22:00，或在已记录睡眠等安排时选择「跟随日历（排除餐休）」。沿用 TickTick 设置中的单行控件，可另设 10–240 分钟的手动每日上限，留空即自动；明确保存过的旧上限会保留，手动上限同样受当天剩余时段约束，不在每次执行时重置。

Outlook 与 TickTick 的具体时段取占用区间并集；同名且唯一对应的事项采用 Outlook 的预约时段，不重复扣除，重名歧义不猜配。正在进行的日程只占之后的部分；预约已经过去但仍未完成的固定普通任务，需要从剩余空档重新预留；重要事项不额外预留，但尚未结束的实际日程或定时区间仍算占用。已完成的普通任务仍计入当日用量，已被日历占用覆盖的完成事项不再扣一次；全天用量只作为防止无限回填的上限，不能增加当天剩余空档。普通任务须能放入连续空档，多个碎片不能拼作一个长任务。用时优先读取任务描述（content，其次 desc）的括号标注，如 `(1m)`、`（1h）`、`(1h1m)` 分别为 1、60、61 分钟；支持中英文括号、空格及大小写，取首个完整有效标注，不把组合时长误计为末尾分钟。没有描述标注时才读取标题／标签或已设时间区间，再回退到默认估时；重要事项、今日总量和完成记录都沿用同一口径。周期紧迫程度及最近实际完成时间决定挑选顺序，周期分摊值仅留作记录，不再限制当轮分钟数；有空档时可从明日事智能清单（无日期、逾期和未来 30 天）补入符合条件的普通任务，直到没有更多符合场景、连续空档及喷雾规则的任务，不要求凑满。定时事项及超出清单范围的未来安排不提前拉回，原周期截止日不随延期后移。容量不足时显示周期紧张及暂无空档数量，不承诺全部按期完成。

DoneList 的「重排今日事」读取最新剩余空档及完成记录，仅改动剩余普通今日事和从明日事中选中的补入任务日期，不运行完整同步，不修改标签、训练、洗衣或 Outlook 日程。点击带虚线下划线的排期结果可展开本次快照：剩余时间、日程占用、重要事项估时、所选任务及依据；旧快照保留当时的规则与数值，新规则在下次手动重排或自动排期后反映。

完成历史首次分段读取近 60 天，后续增量读取并持续保留每个任务及重复系列最后一次完成；同清单、同父任务、同名且唯一的重复系列可匹配不同历史 ID。同名歧义不猜配；无可用完成记录时按创建时间排列。读取失败停止本轮每日安排；只有日期写入及回读成功后才发布本次安排状态。每日排期和场景排期先合并再写入，保留循环起算方式与规则，避免重复同步往返改期。

「夜间routine」按任务自身的开始时间自动切换 `routine` 标签，识别名称时忽略空格和英文大小写。开始前加上，开始后移除；未来日期的重复实例始终隐藏，当天已过但未完成的实例在跨日后也重新隐藏，等当晚开始时间再显示。按任务时区判断，未设时区则沿用连接时区；无有效开始时间、全天或已完成任务不修改。为满足「今天重要之事」的高优先级条件，夜间 routine 设为高优先级；其他标签、提醒、内容、日期及重复规则保留，更新后回读验证。是否进入智能清单仍取决于该清单的日期等其他筛选条件。

`.github/workflows/ticktick-night-routine.yml` 每天北京时间 22:00 处理夜间 routine 和未完成运动，00:00 临时隐藏四个智能清单内的待办，05:00 恢复临时标签后处理夜间 routine 和运动。夜间未完成训练跳至下一次符合场景及经期规则的原定训练日，不记为完成。沿用已有 `BONBILLS_CRON_SECRET` 和写锁，不刷新 Outlook 或归档。普通 GET 不执行修改，手动执行需认证 POST。GitHub 定时可能延迟或跳过，不能保证恰在整点切换。

“洗头”待办按北京时间在 20:00 前保留 `routine`，20:00 后移除；只匹配标题为“洗头”的未完成任务，保留日期、优先级、重复规则、其他标签和洗头日期跟随关系。凌晨复用现有静默流程重新隐藏，05:00 的临时标签恢复不移除洗头的标签。`.github/workflows/ticktick-daily-plan.yml` 仅在 20:00 那次运行增加一次轻量检查，并在当天安排重算前完成；没有额外轮询。

“洗衣服”复用上述四次日常同步，按最近实际完成日期和原重复规则计算周期目标日，在目标日前一天至后两天内选日期；未取得完成记录时保留首次原日期作锚点，改期不会移动整个窗口。若周期目标日落在出行期间，固定到该次出行前一天，优先于天气窗口、场景和空闲预算；出行按日历旅标签及手动拆分识别。若出行前一天已经洗过，下一周期不重复倒排；错过前一天时保留待办等待补做。目标日不在出行期间时，继续满足寄／居／旅、Outlook 空闲及餐休限制，再优先洗衣当天及次日连续晴朗、前一天也晴朗的日期，其次连续无雨，再比较雨量、降水概率、日照；天气相近优先靠近周期目标。天气来自 [Open-Meteo](https://open-meteo.com/en/docs)，固定使用「对账 → 设置」保存的“居的城市”（同处也可设置“寄的城市”，随账单配置同步），不随定位或旅行目的地切换，每地点缓存 3 小时。缺地点、预报不完整或过期、没有合适空闲、超过预报范围时保留排期，随下次同步重试；不会无限顺延。保留原时刻、重复规则、优先级和标签，固定时刻冲突的日期不入选；已完成任务与模板不改动，普通场景和每日轮换不覆盖洗衣日期。

凌晨临时隐藏按 2026-10-05 从 TickTick 读取的四个智能清单条件取并集：`🍌今日事` 为今天的 0/1/3 优先级任务，`🍌明日事` 为无日期、逾期或未来 1–30 天的 0/1/3 优先级任务，两者排除 `routine／不关我事`；`‼️今天重要之事` 为逾期或今天的优先级 5 任务，只排除 `routine`；`❕明日之重要事` 为无日期或未来 1–21 天的优先级 5 任务，排除 `routine／不关我事／当天`。使用任务自身截止日期和时区；日后修改智能清单条件时需同步更新此规则。

仅给原本不带 `routine` 的任务添加临时标签。写入前在 `ticktick:sleep-tags:v1:<连接清单指纹>` 持久化所有权，不设置过期时间；05:00 只移除这些记录对应任务的临时标签，保留其他标签、日期、优先级、重复及完成状态。任务改期、移清单、完成或接口响应中断后仍按记录恢复，不重新用过滤器筛选；恢复后夜间 routine 的原显隐规则继续生效。旧的“🐦日常任务”按标题直接删标签规则已被替代，原生 routine 标签保持不动。每批最多处理 20 个任务，写后回读，工作流在同一次执行内继续未完成批次；原有四次每日排程先补完待恢复的标签，避免把暂时隐藏的任务当作永久 routine。这里仅执行普通脚本，不调用 AI 模型。

每次连接及同步都在所有清单和收集箱中只按任务名称查找模板，不限定清单名称、标签、父任务或完成状态，也不使用旧任务 ID 判断模板是否存在。优先查找 `出门todo模版／出门todo模板`，兼容旧名称 `出行todo模板／出行todo模版／出门todo／出行todo`；匹配到多个同级名称时明确报错，带行程前缀的生成副本不会被选中。模板移动或重建后，能按名称及父子关系唯一对应的已有出行、心愿任务会重新关联，保留任务 ID、完成状态、手动日期及原清单；新行程在当前模板所在清单生成。同一连接重新连接模板时不清空已有实例。

## Schwab 同步

Schwab 读作 `/ʃwɑːb/`，近似“施瓦布/什瓦布”。首次使用前，需要在 [Schwab Developer Portal](https://developer.schwab.com/) 创建并获批 Trader API 应用，拿到 app key、app secret，并把 callback URL 配成和本地一致，例如 `https://127.0.0.1:8182/`。

本地新建 `.env.schwab.local`，填入：

```bash
SCHWAB_CLIENT_ID=你的 app key
SCHWAB_CLIENT_SECRET=你的 app secret
SCHWAB_REDIRECT_URI=https://127.0.0.1:8182/
```

首次授权：

```bash
npm run schwab:login
```

脚本会输出授权链接。登录 Schwab 并允许访问后，把浏览器最终跳转到的完整 URL 粘回终端。token 会写到 `.schwab-token.json`，该文件已被 git 忽略。

同步账户、余额、持仓和最近交易：

```bash
npm run schwab:sync -- --days=60
```

默认输出到 `src/data/schwabSnapshot.local.json`，该文件同样不会入库。Schwab 交易查询通常限制最近 60 天，可以用 `--from=YYYY-MM-DD --to=YYYY-MM-DD` 或 `--output=PATH` 调整。
只同步余额和持仓时可加 `--no-transactions`。

## 每日计划简报

登录后访问 `/life?view=briefing`，可读取从当天起未来七天的训练安排、安排原因、预计用时，以及 TickTick「今日事」逐项入选原因与预计总时长。页面通过 `/api/ticktick-trips?action=briefing&format=json` 获取数据，GET 只读；「刷新简报」先执行现有 Outlook / TickTick 排期，再更新训练和完成记录。简报沿用登录保护和禁止缓存设置，不另设公开链接或发送接口。

每日挑选时保存逐项原因，只有任务日期写入成功才发布；失败保留之前的说明。简报以 TickTick 当前任务日期、优先级和标签筛选今日事，排除 `routine／不关我事`。没有同日、同清单、同任务且标题相同的排期记录时，明确标注原因待确认。训练复用 BonLog 的滚动安排，兼容跨月跨年，并标明预测阶段。时长统一标为预估，训练已列入今日事时不重复累计。

每日邮件通过当前 Codex 任务的定时自动化读取此简报，再调用已连接的 Gmail 发送；这里不存储邮件凭证，也不新增 GitHub / Vercel 定时任务。定时运行时须先确认报告日期和数据状态，失败时不把缓存内容作为当天已更新的计划发送。

### 洗衣日程写入 Outlook

支持 Make 免费连接：创建即时 Custom Webhook → Microsoft 365 Calendar / Make an API Call → Webhook response 场景，用 Make 自带微软连接授权 `offline_access`、`User.Read`、`Calendars.ReadWrite`，无需自有 Azure 应用。Webhook 地址是访问凭据，不公开、不写日志或仓库；在「BonLog → DoneList → 洗衣日程 · Outlook」输入后只读验证可写日历，选择目标日历再开启。地址以 AES-GCM 加密保存在原连接键中，浏览器只暂存于输入框，不持久化。

Make 输入为 `path`（Graph `/v1.0/me/calendars…` 相对路径）、`method`（GET/POST/PATCH）、`body`（JSON 文本）、`headers`（key/value 数组）；固定发送 Graph `Prefer: IdType="ImmutableId", outlook.timezone="Asia/Shanghai"`，有 ETag 时发送 `If-Match`。回传 HTTP 200 JSON `{ "protocol": "bonbills-outlook-v1", "status": 200, "body": <Graph 响应对象> }`，错误分支也返回真实 Graph 状态（尤其 404/412）。Make 默认纯文本 `Accepted` 不视为执行成功。场景只放行所选日历的事件及必要的日历列表查询，不连接其他业务模块。

Make 模式同周期排期指纹未变且已回读验证时不发请求；发生变化仍核对归属、参与人及版本。后台通过 Redis 原子计数，滚动 32 天最多发送 200 次请求（含失败），不因重连重置；达到上限暂停，不自动购买额度。标准三模块场景约 600 credits，错误分支或其他 Make 自动化也占用同一免费额度。没有保持日历轮询，因此手动改动在下次洗衣计划变化时才重新检查；断开后原日程保留。

自有微软应用方式仍提供独立写入连接。首次需要在自己的 Microsoft Entra 租户注册应用，支持“任何组织目录中的帐户和个人 Microsoft 帐户”，在“身份验证 → 高级设置”启用“允许公共客户端流”，并添加 Microsoft Graph **委托**权限 `Calendars.ReadWrite`。把应用（客户端）ID 填入设置，点击“登录微软授权”，在微软官方设备登录页面输入短授权码并同意；无需应用密钥，也不要把访问令牌粘贴到网页。随后选择目标「日历」并开启同步。若已有应用 ID，也可用 `OUTLOOK_CLIENT_ID` 预填。微软侧的权限范围是日历读写，应用代码仅写所选日历中与洗衣任务明确关联的日程，不添加参与人。

连接申请 `offline_access` 和 `Calendars.ReadWrite`，遵循微软设备授权轮询间隔与过期时间。设备凭据、访问与刷新令牌使用 `SYNC_SECRET` 派生密钥 AES-GCM 加密存储；只允许已登录同源请求管理连接，并与定时写入共享锁。连接与 ICS 订阅相互独立。当前 Codex 的 Outlook 连接不会被复制到 BonBills 后台，也不会导出其中的令牌。

每天现有四次 TickTick 排期完成后同步洗衣日程，保持原待办时刻（全天待办取 08:00），时长复用描述估时，未标注且无时间范围时为 50 分钟。不创建固定五天重复日程：同一实际完成周期使用同一标识，天气或出行改期更新原日程；实际完成后再开始下一周期，保留旧日程。创建前持久化 transactionId，并通过扩展属性查回丢失响应，避免重试重复。改期校验事件归属与 ETag；用户已删除的本周期日程不重建，已改名或添加参与人的日程不覆盖；手动同名日程不认领。失败显示在连接状态并令定时工作流报告失败，不回滚已经完成的 TickTick 排期。断开会清除后台令牌并停止写入，保留已创建的 Outlook 日程。
